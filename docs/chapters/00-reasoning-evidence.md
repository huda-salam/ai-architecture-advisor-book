# 0. Reasoning & Evidence Standard

This handbook distinguishes between what is known, what is inferred, what is assumed, and what is recommended.

## 0.1 Evidence categories

| Category | Meaning |
|---|---|
| **Fact** | Supported by authoritative or directly verifiable evidence. |
| **Theory** | Supported by established academic or conceptual theory. |
| **Industry evidence** | Documented real-world implementation or outcome. |
| **Technical evidence** | Standards, architecture documentation, specifications, benchmarks or primary technical documentation. |
| **Inference** | Reasoning derived from available evidence. |
| **Assumption** | A proposition currently accepted for analysis but not yet established. |
| **Recommendation** | The advisor's judgment based on the preceding reasoning. |
| **Uncertainty** | A material issue that remains unresolved. |

## 0.2 The recommendation chain

```text
Requirement
    ↓
Constraints
    ↓
Evidence
    ↓
Assumptions
    ↓
Analysis
    ↓
Alternatives
    ↓
Trade-offs
    ↓
Recommendation
```

## 0.3 Confidence

Important recommendations should state confidence where uncertainty is material:

- **High** — strong evidence and limited material uncertainty.
- **Medium** — reasonable evidence but meaningful assumptions remain.
- **Low** — insufficient evidence; recommendation is provisional.

## 0.4 What would change our mind?

A strong recommendation should identify the evidence or condition that could invalidate it.

This prevents technical advice from becoming ideology.

## 0.5 Source discipline

Important claims should preferentially use:

- peer-reviewed research;
- established theories and standards;
- primary technical documentation;
- technical and security standards;
- documented industry implementations;
- corporate disclosures and case studies;
- direct measurements and experiments.

Rapidly changing claims about models, platforms, APIs, pricing or regulations should be re-verified against current primary sources before being treated as current fact.
